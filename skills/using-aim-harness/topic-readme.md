# Topic README — 세션 재개 지점 + 산출물 Context Map

`../agent/prompt/<topic>/README.md` 작성 규약. `using-aim-harness`의 **Topic README (필수)** 항목 상세.

> **작성 주체는 에이전트다.** 이 문서의 모든 생성·갱신 동작(README 작성, 재개 지점 갱신, Context Map 유지,
> 인덱스 재생성)은 작업 중인 에이전트가 스스로 수행한다. 사용자에게 요청하거나 미루지 않는다.
> 재개 지점·확정 사실은 **그 세션을 수행한 에이전트만 아는 정보**이므로 애초에 위임할 수 없다.

## 왜 필요한가

세션은 예고 없이 끊긴다(컨텍스트 한도, 도구 오류, 사용자 이탈, 호스트 재부팅). 끊긴 시점이
`closing-session-aim` **이전**이면 종료 절차는 아예 실행되지 않는다. 따라서 재개 정보를 종료 시점에
쓰는 설계는 원리적으로 실패한다 — **topic 디렉터리를 만드는 순간 README를 함께 만들고, 작업 경계마다 갱신**한다.

산출물이 5개를 넘어가면 파일명만으로는 읽는 순서와 최신본을 알 수 없다. Context Map이 그 비용을 없앤다.

## 언제 쓰고 언제 갱신하나

| 시점 | 동작 |
|------|------|
| topic 디렉터리 최초 생성 | README.md 동시 생성. 최소 Status + 재개 지점만 채워도 된다 |
| 작업 경계(결정·완료·블로커·중요 발견) | 재개 지점 갱신 + 새 산출물을 Context Map에 추가. journey-log 기록과 같은 타이밍 |
| 산출물 파일 추가/개명 | Context Map 행 추가 |
| 세션 종료(`closing-session-aim` 3-F) | 최종 정합성 점검 — 갱신 누락분 반영 후 commit |
| DONE 이관 | Status를 `완료`로 바꾸고 결과(MR·커밋·문서 링크) 명시 |

## 템플릿

```markdown
# <topic> — <한 줄 요약>

> **Status**: 진행 중 | 대기(<사유>) | 완료
> **Updated**: YYYY-MM-DD

## 재개 지점

- **지금 상태**: <직전 세션이 끝난 지점. 무엇이 됐고 무엇이 안 됐는지>
- **다음 할 일**: <바로 실행 가능한 액션 1~3개. "검토한다" 말고 "X 파일의 Y를 Z로 고친다">
- **블로커**: <있으면. 없으면 행 삭제>
- **주의**: <이 topic 고유의 함정. 없으면 행 삭제>

## Context Map

| 파일 | 내용 | 읽는 시점 |
|------|------|----------|
| `analysis_report.md` | 증상·근본원인·판정 | 배경 파악 |
| `design_spec.md` | 설계 결정과 대안 | 구현 전 |
| `plan_tasks.md` | 태스크 분해·체크리스트 | 실행 중 (진척은 여기 체크박스) |

## 확정 사실 (재조사 금지)

- <이미 검증돼 다시 조사할 필요가 없는 것 + 근거 파일>

## 결정 · 발견 로그

- YYYY-MM-DD: <결정 또는 발견. 한 줄>
```

**확정 사실** 섹션은 재조사 낭비를 막는다. 이전 세션이 워크플로·실측으로 확정한 것을 다음 세션이
처음부터 다시 파는 것이 재개 비용의 큰 부분이다. 근거 파일을 함께 적어 신뢰 근거를 남긴다.

**빈 섹션은 지운다.** 채울 내용이 없는 표는 재개 비용을 오히려 늘린다.

## 2층 구조 — 루트 README와의 관계

| 파일 | 범위 | 성격 |
|------|------|------|
| `prompt/README.md` | 전체 topic **인덱스** + 폴더 구조 규약 | Context Map은 **생성물** — `agent/script/prompt_index.sh` 출력 |
| `prompt/<topic>/README.md` | 그 topic **내부** — 재개 지점 + 산출물 맵 | **SSoT**. 첫 줄 `# <topic> — <한 줄 요약>` 이 루트 인덱스의 원천 |

루트에 topic 내부 진척을 적지 않는다. topic README에 다른 topic 사정을 적지 않는다.
**루트 Context Map은 직접 편집하지 않는다** — 스크립트를 돌려 그 출력을 붙여넣는다. 같은 정보를
두 곳에서 각각 서술하면 반드시 갈라진다(실측: 작성 하루 만에 drift 4건).

첫 줄 형식이 곧 인덱스 항목이므로 `# <topic> — <한 줄 요약>` 형식을 지킨다.
`# Context Map — ...`, `# Handoff: ...` 처럼 문서 종류로 시작하면 인덱스에 그 문구가 그대로 실린다.

## handoff.md 는 만들지 않는다 — README 로 단일화

**진입 파일은 `README.md` 하나다.** 과거 관행이던 `handoff.md`(세션 이관 문서)는 신규 작성하지 않고,
그 내용(재개 지점·확정 사실·다음 액션)을 README의 **재개 지점** 섹션에 담는다.

이유는 실측이다 — 병존하던 topic에서 진입점 지정이 서로 반대로 갈렸다.

| topic | README | handoff |
|-------|--------|---------|
| `oftop` | 파일 지도·결정 이력 | "**이 파일이 진입점이다**" 명시 |
| `dcnote_5928` | "세션 재개 가이드" | "★★ 현재 재개 지점" — **양쪽 중복** |
| `host_resource_cleanup` | Context Map·결론 | "재개 방법"·실행 명령 — **양쪽 중복** |

`dcnote_5928`의 handoff에는 `## ★★ 2026-08-10 갱신 — 현재 재개 지점 (아래 구절보다 우선)`이라는
헤딩까지 생겼다. **한 파일 안에서조차 최신 위치를 표시해야 할 만큼** 재개 정보가 흩어져 있었다는 뜻이다.

**분리해도 되는 것**은 이관 서술이 아니라 *성격이 다른 산출물*이다 — 실행 명령 묶음(`runbook.md`),
설계(`design_spec.md`), 조사 결과(`analysis_report.md`). 이들은 README Context Map에서 가리킨다.

기존 `handoff.md` 보유 topic은 다음 세션이 그 topic을 만질 때 README로 흡수한다(일괄 마이그레이션 불필요).

## Common Mistakes

- **종료 시점에 몰아 쓰기** — 비정상 종료 시 그대로 유실. 규약이 존재하는 이유 자체를 무력화
- **"다음 할 일"을 추상적으로** — "리뷰 마무리" 대신 "`02_code_review.md` High 3건을 MR !658 discussion으로 등록"
- **Context Map을 `ls` 복사로 채우기** — 파일명은 이미 `ls`로 보인다. *내용*과 *읽는 시점*이 값
- **Status 방치** — 완료된 topic이 "진행 중"으로 남으면 다음 세션이 재개하려 시도
- **루트 README 갱신 누락** — topic 신설 후 인덱스에 없으면 `ls`로만 발견 가능

## Red Flags

- "이 topic은 짧아서 README 불필요" → 짧을 거라는 판단 자체가 세션 끊김 이후엔 사라진다
- "handoff.md 있으니 README 생략" → 진입 파일은 README 하나로 단일화. handoff 신규 작성 금지
- "재개 정보는 handoff, 지도는 README로 나누자" → 그 분리가 만든 중복이 본 규약의 원인이다
- "다음 세션에 내가 기억함" → 다음 세션은 컨텍스트가 없는 다른 인스턴스다
- "README 정리는 사용자가 할 일" → **작성 주체는 에이전트다.** 재개 지점은 이 세션을 수행한 쪽만 아는 정보라 위임 자체가 불가능
- "사용자에게 README 갱신을 물어본 뒤 진행" → 확인 대상이 아니다. 산출물 생성과 동일하게 그냥 수행한다
